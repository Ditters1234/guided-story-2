# AI world authoring

The world workspace's **AI world tools** button creates a node or a group from an idea. Any node's inspector offers **Generate / revise with AI**, and each connection offers **AI…**. Both use the same schema-driven service and review panel, including custom node types and capability fields. AI support is a service over world nodes; connection clients, credentials and job state are not embedded in each node.

The initial [composable-node revision](WORLD_NODE_DESIGN.md) adds richer field semantics, useful bundled presets and shared story/image projections through this same pipeline. Typed relationship details use the same pipeline; situated knowledge remains later work. Optional fields may be absent or null; zero and false retain their distinct meanings. Native choice/reference checks and checked-field protection apply to custom extensions too.

The footer's **Prompts** shortcut opens **Settings → Prompts → World creation & rerolls**. Edit the full shared instructions there, save, then return to your retained draft. Per-request direction stays in the authoring dialog. [Prompt settings](PROMPTS.md) documents the other tools and save behavior.

## Create, review and apply

1. Open a saved project and configure **Settings → LLM**. The offline demo exercises the review flow without contacting a model.
2. Choose **Build a world from an idea**, **Create a connected group**, or a node preset. Empty stories default to world building; populated stories default to group creation. Choosing a character preset enables related nodes, including custom presets with the character capability; you can turn this off for a single-record request. The current response limit is 20 nodes and 80 links.
3. Add direction and context references whose full details must be included. Group creation also checks a bounded existing-world index and relevant records automatically. A new group's current map selection starts checked as a full-detail reference. Other creation/revision paths keep their explicit source scope. Expanding the map does not send the entire world.
4. Generate once, then review the proposed records and links. Edit their fields manually, add/remove proposed group members and links, or edit retained JSON when a response needs repair. Invalid proposals stay saved and editable.
5. **Apply proposal** validates the whole resulting world and commits the group together. Until then, the established world is unchanged.

**Build a world from an idea** asks for a starting setting, cast and relevant belongings. **Create a connected group** asks for only the requested set, such as camping equipment, several locations or a cast addition. Under **Group node types**, choose **Mixed types, as requested** or a single saved preset such as **Item only**. A type-limited group's output schema and native validation restrict every new node to that preset; the candidate editor's add-node menu uses the same limit. Custom presets work identically. A container and its contents can all be item nodes with appropriate capabilities. To include characters together with garment items, use mixed types; a character-only group leaves clothing to a separate item request.

Group creation automatically supplies a compact catalogue of existing names, IDs, types, capabilities and physical placements. It searches current-world names and short text locally for relevant matches, prioritizes selected/named records, and follows up to three physical hops to include belongings, worn items and nested container contents. At most 100 index entries and 12 additional full records fit within a 24 KB optional-context ceiling and the actual request allowance. Full records are included whole or omitted; explicit references and required instruction nodes are reserved first. **Existing world context** shows indexed/full-record coverage, names, placements and omissions. A partial index is not a claim that the model examined every record's full text.

New links may start at proposed nodes and target existing IDs actually supplied through the captured index or explicit references. Select owners/places under **Context references** when their full details must be included. Neither creation option replaces established records, resets the story or moves existing possessions. The native backend captures the read scope with the source world and rejects unexposed targets, forged context and stale results. Reopened candidates show their captured context; reroll to use changed context. Matching existing names produce advisory warnings so intentional additional units remain possible. A group may return no new nodes; the panel explains the empty result and does not publish an empty transaction.

Switching creation choices preserves direction/references and resets incompatible scope controls. Rerolls and reopened drafts retain their saved scope. Older combined world/group requests keep their original world-building meaning until you choose a new scope in a fresh candidate; no existing draft is silently repurposed. Older generated group candidates need a fresh reroll to capture the new existing-world context; retained output is preserved.

For an existing node, check the fields AI may change and choose **Generate details**. Descriptions can be blank, and direction is optional: leaving it empty asks AI to develop checked fields from the node's name, type, existing facts and supplied context. This also fills missing optional custom fields without placeholder text. Populated checked fields can be revised or rerolled through the same flow. Name is protected by default. Unchecked fields, node types, capability sets and existing links cannot change in a revision proposal. Custom fields use the same rules as built-in fields. Changed references may point only to explicitly exposed records. Creation can attach new nodes to supplied existing references; it cannot move or rewrite those existing nodes.

When a target node is also included as story-wide AI context, it is supplied as editable source for its own revision, with its intended context role/tool configuration. Its empty body does not block generating that body, and its instructions do not govern their own rewrite. Other required context still applies. Apply changes only the checked node fields and preserves its inclusion configuration. New-node/group creation still requires an idea.

Creation develops missing details rather than copying age/role labels into names. The contract asks for personal names, concise structured profile/personality/goals/voice/appearance fields, with supplementary notes for additional detail, while preserving explicit author choices. World building and explicit people bundles with item types permitted request individual garment items with wearable coverage/layer values and one worn-by physical placement. This does not add people or places to an item group. Wearing includes inventory membership; carried or stored items use stored-in instead, never both for one item. World-building and character-root requests receive a schema-derived garment example; custom item presets use the same pattern. Garment detail belongs to the item so changing clothes does not require rewriting a character's body description. Output sizing now accounts for the selected preset's field count, with a compact suggested group and a hard 20-node limit. The prompt prioritizes the requested set or typed root, omits optional extras unless requested and uses compact JSON/empty redundant notes to leave room for links and closing structure.

The candidate editor lists each proposed character's **Worn items**. **Add worn item** creates a separate item with one wear placement; select it to edit its name, appearance, coverage and layer. Generic **Add capability** uses project-defined defaults. A nonblocking warning highlights characters with no linked clothing, allowing intentional unclothed characters. These controls edit only the saved proposal until Apply. Existing characters and earlier accepted worlds are never automatically renamed or redressed. Name changes in targeted rerolls require checking Name.

**New candidate / reroll** starts a separate saved draft with the same direction and scope. It retains the previous candidate, including manual edits. **New creation** starts a fresh creation request from any review. The saved-proposals list reopens older work. Revision of existing relationships continues through the manual connection tools; AI relationship transfers are not part of this slice.

Use **Delete draft** beside an entry in **Saved proposals**, or in the current draft's footer, then confirm. This removes an unapplied draft/candidate without changing world records or other proposals. A running request must finish or stop first; applied proposals remain protected. Deleting the current proposal closes its panel without creating a replacement. The 200-proposal limit counts remaining proposals, excluding deleted drafts. Small deletion markers prevent delayed saves/retries from recreating the deleted ID.

## Settings and API behavior

The native client sends non-streaming requests to a configurable [Chat Completions API](https://developers.openai.com/api/reference/resources/chat/subresources/completions/methods/create). Enter the API base URL and optional key, then **Test connection** to fetch the server's [available models](https://developers.openai.com/api/reference/resources/models/methods/list). Select a returned model; a sole model is selected automatically. A saved model remains selected after reopening, without a hidden network request. Changing the endpoint/provider/key clears the fetched choices until the next test. A base ending in `/chat/completions` is also accepted. Advanced controls select JSON object, JSON Schema (non-strict), or prompt-only output, and `max_tokens` or `max_completion_tokens`. Server support varies; no real-provider generation compatibility has yet been certified.

The configured context/output allowance is checked before submission using a conservative byte-based estimate, not an exact provider tokenizer. A generation makes one provider request, with no automatic retries, redirects, repairs or provider switching. Timeout, response size and group size are bounded. The connection test makes one bounded `GET /models` request using the saved key, with no model or text generation required. It checks the model-list endpoint, not every model's generation capabilities. Empty/malformed catalogues and credential errors are reported. Opening settings does not contact a provider. The offline demo is deterministic sample data, not an LLM.

New connections use [Qwen-oriented local 30B defaults](MODEL_TARGETS.md): temperature 0.7, top P 0.8, top K 20, min P 0, and thinking disabled through the chat template extension. Existing files preserve their saved choices and load absent new fields as generic compatibility defaults. Use **Sampling & API compatibility → Use Qwen 30B defaults** to opt in on an existing connection; choose the thinking transport supported by your server. Blank Top K/Min P and Server default thinking omit optional extensions. Revision context excludes unrelated schema definitions, and schema mode sends the output schema only through response_format. The composable-field contract uses fingerprint version 5: earlier generated proposals become stale while their drafts and edited output remain available for review/reroll.

Connection settings live in `llm-connection.json` in the per-user app config directory, separately from stories and appearance preferences. **Save connection**, closing settings and normal app shutdown flush pending connection edits. Windows DPAPI encrypts API keys for the current OS user in separate credential files. Keys are not returned to the frontend after saving and are not written into proposals or story snapshots. Copying a story does not copy connection credentials.

The settings body scrolls within the window while **Test connection**, **Save connection** and **Done** remain visible in its footer. Saved-key confirmation is displayed next to the empty replacement field; an empty field retains the saved key. Save errors and pending/success status are also shown in the footer.

## Drafts, interruption and source changes

Prompts, scope, original extracted provider text and manually edited candidate JSON have separate saved fields in the story's `proposals/` directory. Candidate edits autosave with independent versions. Complete thinking/code-fence wrappers are stripped from response text; the full HTTP envelope and provider reasoning are not stored. Truncated output is retained and cannot be applied until manually edited/reviewed or replaced with a new candidate.

One generation can run at a time. The panel can close while generation continues and the world remains editable. Cancel stops the local request; a remote server may continue its computation. Normal shutdown stops active work before closing. After abrupt termination, a saved running job becomes interrupted when the project reopens; it is never resent automatically. A result that cannot be saved is retained in the running app with an error, and project switching/closing is blocked until its save succeeds. Abrupt termination during that disk failure can still lose the in-memory result.

Each generation captures an immutable source snapshot and a fingerprint of the selected records, schema, direction, scope, connection settings and prompt contract. Relevant changes block Apply; unrelated record edits and map layout changes can coexist. Applying revalidates against the latest world and preserves unrelated work. Request receipts reconcile an apply that committed before its status write completed, so retrying does not duplicate a group.

These world foundation/revision tools share their connection and single active-request limit with the [passage composer](STORY_AUTHORING.md), explicit [chapter-summary tools](MEMORY.md) and optional [image prompt tools](MEDIA.md). Passage prose, effects review, acceptance, chapter plans, history/forks, text/event revisions and bounded older-context retrieval are implemented as a prototype. Reviewed media adds saved node images and passage illustrations through import or explicit ComfyUI submission. Image prompt proposals use captured visible facts and require Apply to an image draft before separate generation. Belief filtering and further long-story compaction remain future work.

## Existing relationship revision

Use **Connections → AI…** to develop or reroll checked notes/properties, including empty values. Selected endpoints supply read-only context; they are not editable node targets. The request may contain up to 12 combined node/link targets and 200 combined checked fields; additional explicit node references retain their separate 12-record limit. Mixed node/link requests use the same native service and source checks. The UI currently starts from one selected node or connection.

Native validation requires exactly the requested records and preserves unchecked fields, IDs, relationship types and endpoints. Typed references may change only to supplied nodes; unchanged existing pointers may remain without expanding their referenced records. Creation groups may add rich links from new nodes to captured references, never revise an existing link or placement. Captured requests/results survive restart and remain subject to stale-source, Apply and receipt checks. The editable World creation & rerolls prompt includes this contract; user overrides remain authoritative saved instructions, while native validation is always enforced.

## Event authoring

Event uses the same preset/extension fields, empty-field development, checked-field protection and explicit Apply as other nodes. World AI may propose author-established backstory; future intentions belong in plans/threads. Creating an Event or its descriptive links never executes consequences. Source annotations are read-only context metadata outside the node output contract. Native publication supplies author provenance for world additions, or exact passage/version/effect citations when prose-derived Event cards are approved and accepted. Full source-anchor prose is not automatically recalled. See [sources](SOURCES.md).
