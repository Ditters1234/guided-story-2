# Passage authoring and history

The Story workspace uses the same composer for the first passage and every later passage. Its left pane holds chapters, passages and saved drafts; the center is for prose; the right pane holds scene planning, world-change review or accepted-passage details. Switching to World restores the world tree/map/shared inspector. This is a bounded prototype, not yet the full editing/media/memory design.

The toolbar's **Prompts** shortcut opens the full passage-writing instructions, or wording instructions for a wording draft. **Settings → Prompts** also exposes world-change extraction, chapter memory and the other AI tools. These are device-wide defaults; scene/chapter direction remains in this composer. See [prompt editing](PROMPTS.md).

## Write and review

1. Open **Story**. The scene starts from the selected place/character, or a retained scene choice, with nearby characters offered as an editable cast. It includes at most 12 other participants and does not pull in the whole map. Chapter/passage titles and a word target have usable defaults. Edit viewpoint, location, participants, references and direction as needed. New passages inherit an open chapter's plan; closing a chapter offers a new editable plan on the next writing action. Opening a composer makes no model request.
2. Choose **Generate passage** in the fixed toolbar above the center editor, or write prose manually. A manual outline is optional: with blank passage direction, the model develops the next scene from the selected world, chapter direction and accepted history. The chapter-plan fields currently support manual editing; AI chapter-plan proposals remain future work. Generation makes one explicit narration request using the configured connection. **Generate new candidate** preserves the existing draft and creates a separate candidate.
3. Edit the retained prose, then choose **Check world changes with AI** beside Accept in the fixed footer for one explicit extraction request. The right pane shows a card for every proposed node creation/update, connection change/removal and continuity note. The footer labels generated/saved candidates as not accepted; saving prose is not story acceptance.
4. **Approve**, **Edit** or **Remove** each card independently. Node editors expose descriptions and project-defined capability fields; connection editors expose source, relationship and target. Source quotes can be edited or chosen from the passage. Removing a new node previews its dependent proposals/notes; rejecting a movement also includes its paired old-placement removal. These operations affect only the draft. After edits/removals, choose **Validate reviewed changes** for native validation without another API call. Every included card needs approval; **Approve all** is an explicit shortcut for a checked set. **Use no world changes** clears the proposals and validates an unchanged world without an AI call. **Advanced JSON** is an optional repair fallback, collapsed by default. The AI can suggest a chapter ending; **Close chapter after this passage** remains the author's choice.
5. Choose **Accept passage** when the set is checked and approved. This publishes prose, chapter membership, notes and the resulting world together. Card approvals, saved drafts and successful checks do not advance the established story by themselves. Editing checked prose disables acceptance again until it is rechecked and reviewed.

Extraction uses concrete schemas for the captured existing nodes and permitted creation presets, including custom capabilities and typed relationship fields. Existing-node branches pin their IDs, types, actual capability sets and protected planning values; new nodes use declared preset fields and relevant optional inventory/anatomy extensions. Link references are constrained to captured records or new aliases, and removals name captured links. Compact field metadata retains kinds, choices, defaults and task meaning without repeating descriptive help in the grammar. Schema conformance does not prove evidence, unchanged unrelated facts or semantic correctness. Native batch validation and card review remain required.

The provider response separates node updates, link updates and removals into explicit operation arrays. The backend converts these declarations to the same individual cards without deduplication, inferred facts or publication; original response text stays retained. This avoids a mixed-operation schema union that made the tested local decoder repeat removals. Legacy/manual flat effects remain supported. Wrong operation groups, malformed responses and cutoffs remain blocked and preserve the full passage. Combined native limits and per-card approval rules still apply.

Drafts autosave separately from accepted records, including incomplete titles. Generate/Validate enforce usable titles and a 100–1,500 word target. The word target guides generation; it is not a minimum-length acceptance rule. The offline demo is short deterministic sample text, visibly labeled, and makes no model request. Context details retain narration/effects provider labels; no credentials are stored in the story.

Use **Delete draft** beside an entry under **Drafts**, then confirm, to remove an unaccepted passage, wording/event revision or reroll candidate. Other candidates and accepted sources stay intact. A running draft must finish or stop first. Deleting the current draft opens another saved draft or the latest accepted passage; if neither exists, use Write next passage to begin again. No replacement draft is created by deletion. Native version checks reject stale deletions, and compact deletion markers keep delayed saves from resurrecting removed work. Markers travel with backups; existing immutable draft versions/history are retained.

The generation toolbar and acceptance footer remain outside the scrolling prose area. Other running text jobs show a visible reason when generation is unavailable; LLM settings stay beside Generate. Wording polish still requires explicit wording direction. The optional-direction contract updates pending passage source fingerprints, preserving their prose/effects for review and rechecking rather than automatically accepting older checks.

Editing prose, plan or effects invalidates its check immediately. Changes to selected world context, recent history or connection settings also block acceptance until rechecked. Changing only the chapter-closing choice does not need another model request. Explicit manual validation checks against the current world; inspect any stale effects before deliberately validating them again. Acceptance revalidates against the latest world and preserves unrelated current edits.

Passage fingerprints include the effective Passage, Effects and Wording system messages and the concrete effects schema, including compiled defaults when no prompt override is saved. Updating these contracts invalidates dependent pending checks without discarding retained prose/effects or altering accepted history. Recheck the saved passage against its supported source before accepting it; no regeneration or acceptance is triggered by opening it.

Card approvals autosave and survive reopening. Editing a card invalidates its approval, along with approvals that reference its changed proposed nodes, while unrelated cards retain theirs. Prose/plan or scoped-source changes invalidate their associated reviews. Generating new proposals clears approvals even if the model returns identical text. Native validation enforces these decisions; an approved card with an invalid batch still cannot be accepted. Wording-only revisions preserve established effects and use their separate wording review.

Approval and validity are separate. The review header says **All N proposals approved** when review is complete, and lists any cards still needing correction or validation. Connection cards show native errors for missing references, duplicate updates, incompatible endpoints/relationships and competing physical placements. In **Edit → Connection to update**, choose a named existing connection or **Create new connection**; an unknown ID is never silently treated as a new connection. Source, relationship and target remain editable. **Inside** nests places; **Present at** places a character at a place, according to the project's relationship definitions. If both an update and removal use the same record, keep one proposal for that record. Correct the marked cards, approve the changed ones and **Validate reviewed changes** before accepting. No JSON editing or new model request is needed for these connection repairs.

## Scope and effects

Context contains selected viewpoint/participants/location/references, their placement ancestors and directly carried/worn items. It does not expand every container or send the entire map. The current limits are 12 participants, 12 references and 80 contextual nodes. Recent context is the last two accepted passages plus their notes and the active chapter plan. [Chapter memory](MEMORY.md) adds reviewed summaries and older accepted notes, with visible coverage and bounded relevance selection. Character-knowledge filtering, automatic chunking and unlimited long-story recall remain unimplemented.

Effects use the project's generic nodes, capabilities and typed links. They can update scoped nodes, introduce up to 20 new nodes using temporary aliases, add/move/remove links and retain up to 12 continuity notes, within an 80-change batch. Existing node types/capability sets cannot be redesigned by extraction. Schema changes and node deletion use the manual world tools. Placement/wear changes receive the same native validation as manual editing, including storage reconciliation and cycle checks.

Every effect/note needs one continuous, verbatim evidence quotation of 8–600 characters from the current passage, ignoring whitespace differences. The field's presence alone is insufficient: paraphrases, changed punctuation/capitalization and separated excerpts joined with inserted `...` or `…` do not match. Literal ellipses are valid when they occur in the quoted prose. Copy a shorter actual sentence or clause rather than abbreviating a long quote.

Cards mark invalid source quotes and offer **Choose quote from passage**. Correct the quote, reapprove the edited card and **Validate reviewed changes**, or explicitly request **Generate new proposals with AI**. The native diagnostics remain available under Advanced JSON with zero-based paths such as `changes[0].evidence`, distinguishing invalid lengths from missing continuous matches. Prose and original extraction are preserved. There is no automatic repair/retry or acceptance. The extraction prompt and evidence schema explain the same quoting contract. Evidence matching and structural validation cannot prove that an interpretation is correct or complete. Review remains necessary. This slice does not implement general pinned-fact protection or semantic contradiction certification.

## Read, inspect and fork

Chapter **Contents**, **Previous** and **Next** navigate accepted prose. Navigation never generates text. Each passage retains immutable before/after world references. Its **Before/After** controls show those snapshots in the shared tree/map/inspector with a read-only banner. **Current world** returns to current editing. Historical selection, expansion and layout do not save over current layout or facts.

**Fork after this passage** asks for a destination parent folder and creates an independent story, keeping the chosen passage inclusively and its after-world. It copies retained text and required historical world records, rebuilds chapter plans/closing status from retained passages, allocates a new story/operation namespace, and excludes later accepted passages, later manual edits, pending drafts/proposals and app credentials. Entity/passage IDs and original provenance remain stable. A staging folder is validated before publication; failure leaves the source untouched and any incomplete staging folder identifiable. No pre-first-passage fork or operation-level undo is introduced.

## Revise accepted text

**Edit wording** opens a separate saved draft for any accepted passage. Edit manually or supply wording direction and request one **Generate polish candidate** call. Review the struck-through/underlined text comparison, choose **Validate wording**, then **Accept wording only** to confirm that the events are unchanged. The original text remains an immutable earlier version. Chapter membership, scene settings, effects and before/after worlds stay fixed; current manual world edits and later passages are preserved. Structural validation cannot certify that the meaning is unchanged, so author review remains necessary.

If all accepted evidence quotes still occur in the new prose, they anchor to that wording. Otherwise the record explicitly retains the original evidence text/version; the reader labels it **Evidence from earlier wording**. An obsolete quote is never presented as proof from current wording. Continuity notes retain the accepted events with that source label.

**Replace latest events** opens the same passage composer using the latest passage's saved before-world and only the history preceding it. The superseded passage is excluded from model context. Edit prose/plan, check or manually validate its effects, and **Accept replacement** to replace that passage's text/world result atomically, keeping its stable passage/chapter identity. This can replace the first passage too. New candidates/rerolls retain their revision purpose and earlier candidates.

Replacement is blocked when the target is no longer latest, its accepted version changes, or the current world differs from its saved after-world. It does not merge or roll back intervening world edits automatically. Fork after that passage to preserve those edits in the original and replace events in the independent copy. Earlier-event changes continue to use a fork after an appropriate earlier passage.

The reader's **Earlier text versions** shows up to 20 superseded versions, including alternate events, as read-only prose. Older records remain in the project; a full version-history browser is pending. A fork starts a fresh revision history and omits superseded alternate events. It materializes only an earlier wording evidence source required by the retained events, so that source remains readable without the original project.

## Persistence and interruption

New projects start with zero passages. Existing world-only and earlier passage projects load without conversion; optional revision fields default to absent. New accepted story indexes and passage/world records are checksummed immutable JSON. The manifest publishes their references through the existing atomic head protocol. Manual world saves preserve the narrative reference. Receipts reconcile acceptance whose final draft-status write was interrupted, even after later world edits or another text revision. Older app builds may reject new revision records; keep using the current build for these projects.

Earlier pending drafts default to no card approvals, so a nonempty effects set needs review before acceptance. Existing accepted passages and historical world files remain unchanged. The optional draft `approvedEffects` field stores review keys separately from model output; older binaries may reject drafts saved with that field. Continue using the current build after reviewing cards.

Saved candidates have independent versions and archived prior drafts. One text request can run at a time across world proposals, passages and chapter summaries. Narration is persisted before extraction; failed, cancelled or truncated extraction retains prose and original returned output. A source change during extraction cannot silently rebase its check. Reopening marks unfinished jobs interrupted and never resends them. Results blocked by a disk-write failure remain in the running app, with project switching/closing blocked until saved; abrupt termination during that failure can lose the in-memory result.

The index currently allows 5,000 accepted passages and 1,000 chapters; up to 200 unaccepted drafts can be retained. Draft archives have no cleanup interface yet. Historical references are checked when read/forked, rather than eagerly loading every past world at project open. [Media](MEDIA.md) supports accepted passage illustrations, exact source versions and retained-history fork copies; chapter memory is documented separately. The offline wording demo normalizes whitespace in the original text and may produce an unchanged candidate; it is not a model-quality example.

## Significant Event records

Effects extraction can propose a significant Event using the project schema and the usual editable approval card. No per-passage Event is required. Acceptance binds its evidence to the exact native text-version/effect source and commits that citation with the passage and world snapshots. Physical effects are separately evidenced changes, not replayed by the Event node. Wording preserves event identity and labels earlier citations; event replacement uses new identity, and forks retain only applicable source anchors. [Events and sources](SOURCES.md) explains the inspector and validation boundaries.
